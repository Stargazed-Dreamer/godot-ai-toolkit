# Game Jam 团队教训复盘

> 来源：2026-09 一次 game jam 的赛后复盘（10 条原始教训，一字未删地整理）。
> 适用于多人小队 jam / hackathon / 课设等 deadline 紧的项目；每条附 Godot 落地方式。
> 与 [pitfalls.md](pitfalls.md) 互补：那边是 AI 操作编辑器的技术坑，这边是**人**的协作坑。

## 开工前 1 小时：把标准定下来（最值钱的一小时）

| # | 教训 | Godot 落地 |
|---|------|-----------|
| 1 | **需要一个 leader 确定各处标准**：命名规范、常量、文件存储结构，并管理项目进度 | 开工第一件事推举一个标准负责人。TA 不一定写最多代码，但要负责拍板下面所有条目、盯封包时间点 |
| 2 | **游戏关键术语统一**：金钱叫 `money` / `gold` 还是 `coin`？各写各的后期全是转换胶水 | 开工 10 分钟定术语表，写进 AGENTS.md 或共享文档；出现新概念先问"叫什么"再写代码 |
| 3 | **关键数值统一从集中的全局数值处拿，不要单独定义** | 建一个 `scripts/globals/constants.gd`（或 Config 资源），玩家速度/重力/金币分值全放这里，代码里只引用 |
| 4 | **编码风格提前定义好** | 直接采用 GDScript 官方风格（snake_case + 类型标注），有 formatter 配 formatter，别靠口头约定 |
| 5 | **文件存储按场景或功能区分**（UI / 玩家 / 敌人），**不要按文件格式分**（代码 / shader / 图片） | `assets/player/`、`assets/enemies/`、`assets/ui/` 各自内聚；找"敌人的东西"只看一个目录 |
| 6 | **创建项目时统一好基础文件结构**（`scenes/`、`scripts/`、`assets/` 等）；**关键全局工具尽快建立**（`gSignal`、`gDataManager` 等），以免开始后大家各自建立 | 开工半小时内由一人建目录骨架 + Autoload 单例（事件总线 / 数据管理器 / 常量表），push 到仓库大家再动手 |
| 7 | **记得定义游戏窗口大小** | `project.godot` 的 `[display] window/size` 开工就定（如 1152x648），否则每个人屏幕上看到的游戏都不一样，UI 全返工 |

## 开发中：纪律

| # | 教训 | 落地做法 |
|---|------|---------|
| 8 | **先 commit / 保存再切换或做任何危险操作，无论如何！** | 切场景 / 切分支 / 合并 / 改 project.godot / 换插件之前，先把工作区 commit 干净。"我等会儿再存"是丢代码的第一句话 |

## 收尾封包：deadline 的最后一公里

| # | 教训 | 落地做法 |
|---|------|---------|
| 9 | **封包不要拖到最后一秒**：至少预留 1 小时做封包测试（会有很多 bug，以及封包时不小心遗漏的事）；leader 视角：**必须给封包预留 1-2 小时，不可妥协** | jam 结束前冻结功能，全员转"打包 + 实机试玩"。封包必然暴露问题和漏导出的文件——这段缓冲不是可选优化，是必选项 |

## 非技术（但同样真实）

| # | 教训 | 说明 |
|---|------|------|
| 10 | **选一个宽阔的位置坐**，要不然老得给其他人让路；周围有沙发会很舒服 | 连续十几个小时肩并肩写代码，工位宽度直接影响心情和效率。选场地时别只看网速和插座 |

## 一句话版本

> 开工先定标准（术语表 / 集中常量 / 编码风格 / 按功能分的目录 / 全局单例 / 窗口大小），leader 负责拍板和盯进度；开发中先 commit 再做危险操作；结束前留 1-2 小时封包测试，不可妥协。
